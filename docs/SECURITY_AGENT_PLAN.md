# Athena as a general security agent: implementation plan

**Status:** Draft · **Version:** 0.2 · **Date:** 28 November 2026
**Related:** [Research, Nov 2026](RESEARCH_2026-11.md) · [PRD](../Athena%20—%20Product%20Requirements%20Document.md) · [Technical Design](TECHNICAL_DESIGN.md) · [Milestones](MILESTONES.md)

## 1. Purpose and target state

Athena should become a general security agent. It **identifies** threats across code, images, hosts and its own AI agents. It **mitigates** them with compensating controls. It **resolves** them by patching and then verifying the fix. Four rules hold throughout:

- A human stays in control of every change.
- Deterministic policy decides what may happen.
- The model only advises: it gathers evidence, explains it and drafts changes.
- Every action is carried out under a signed grant and recorded in the audit chain.

In one line: the model proposes, policy decides, a human approves, a separate signer issues a grant, the executor acts, and the audit chain records.

### Scope

This plan goes beyond the current PRD in several places:

- PRD §50 (Non-Goals) excludes EDR, IDS and antivirus, SIEM and log analysis, and any inline runtime control.
- `docs/MILESTONES.md` defers cloud asset inventory to PRD Phase 3.
- M7 says breadth comes only "now the loop is trustworthy — and not before".

Decision 6.1 therefore recommends an explicit PRD amendment:

- Detection and telemetry are in scope as **evidence that feeds investigation**, not as a SIEM replacement.
- Runtime control happens **only through executor grants**.

Work that depends on the amendment is grouped in Phase 5, which starts after the trust loop is proven.

### Where Athena is today

The README says M0. The code is about M3 complete, with slices of M4, M6 and M7; M5 is absent.

**Built:**

- **Foundations:** the queue (`core/athena/queue/queue.py`), scheduler leadership (`core/athena/workers/scheduler.py`) and the hash-chained audit log (`core/athena/audit/chain.py`).
- **Inventory and intel:** inventory, Syft SBOMs and the Go node agent (`node/internal/collect/collect.go`); intel from OSV, KEV, EPSS and Vulnrichment (`core/athena/intel/`); correlation.
- **Investigation:** a bounded loop (`core/athena/investigation/loop.py`) with six read-only database tools (`core/athena/investigation/tools.py`) and grounded verdicts, behind a gateway with policy, budget and egress logging (`core/athena/llm/`).
- **Risk:** deterministic scoring, SSVC and deadlines (`core/athena/risk/`). Malware is floored at critical in `core/athena/risk/scoring.py`.
- **M6 slices:** suppression, baselines, in-app notifications, metrics, and CycloneDX 1.6 and OpenVEX exports.
- **M7 slice:** Gitleaks and Trivy scans of the repository working tree.

**Missing or constrained:**

- **Remediation (M4):** only a class plan (`plan_for` in `core/athena/remediation/classify.py`).
- **The executor:** `executor/athena_executor/main.py` idles. The grant **public** key is mounted into the executor and loaded by `ExecutorSettings` (`executor/athena_executor/config.py`) and `GrantVerifier` (`executor/athena_executor/grants.py`). The grant **private** key, generated by `deploy/scripts/gen-secrets.sh`, is never loaded by any service, so no grant can be issued.
- **Resolution:** the `resolved` state is never set.
- **Users:** only one account can ever exist. `_bootstrap` in `core/athena/cli.py` exits once `any_user_exists`, and the bootstrap route in `core/athena/api/routers/auth.py` is the only code that creates a `User`. Separation of duties is impossible today.
- **The finding model** fits CVE × package only:
  - `vulnerability_id`, `component_id`, `match_method`, `match_confidence` and `advisory_revision` are all NOT NULL.
  - The unique key `finding_instance_uniq` is built on `vulnerability_id`, `asset_id` and `component_id`.
- **Database access:** core connects as the Postgres superuser (`POSTGRES_USER: athena` in `deploy/compose.yaml`), so it could drop the audit triggers from migration 0002.
- **Node agent privileges:** `deploy/node/athena-node.service` runs as a non-root user with an empty capability set, `NoNewPrivileges`, `ProtectSystem=strict` and `ProtectHome`. It can observe, but it cannot change anything.
- **Sandboxes:** two already have network access. The git clone uses an unpinned `alpine/git:latest` with `network="bridge"` (`core/athena/scanners/git.py`). The Syft image scan joins `athena-nodechannel` to reach the Docker proxy (`core/athena/scanners/syft.py`, `sandbox_network` in `core/athena/config.py`).

## 3. Phases

**Execution order.**

1. Phase 0 makes it safe to add any path that changes anything.
2. Phase 1 then closes the trust loop: approvals, a patch workspace whose first real action is a pull request, verification and rollback.
3. Phase 2 (low-risk identify breadth) runs in parallel with Phase 1, because it only adds read-only evidence.
4. Phase 3 deepens investigation.
5. Phase 4 adds mitigating actions.
6. Phase 5 (runtime telemetry, detection, cloud posture and enforcement) starts only after the PRD amendment (decision 6.1) and Phase 1's acceptance tests pass on the fixture estate.
7. Track S (self-protection) runs throughout.

Each workstream gives **Build**, **Why** (the motivating research), **Touch** (touch points), **Tests**, **Done when** and **Risks**, where they apply. Migration numbers start at 0021 and are indicative. Every migration needs a working downgrade, because the tests run `downgrade base` then `upgrade head`.

Extension patterns used below:

- **Job kind:** `@handler("x.y")` from `core/athena/queue/registry.py`, imported in both `core/athena/workers/worker.py` and `core/athena/api/routers/jobs.py`. Periodic work goes in `SCHEDULE` in `core/athena/workers/scheduler.py`.
- **Scanner:** `core/athena/scanners/<tool>.py` with `SandboxSpec` and `run_sandboxed` (`core/athena/scanners/sandbox.py`), the image pinned in `core/athena/config.py`. Record results with `start_scan`, `finish_scan` and `record_components` (`core/athena/inventory/service.py`) or `record_code_scan` (`core/athena/codefindings/service.py`). Offer on-demand scans through `SCAN_JOBS` (`core/athena/api/routers/assets.py`).
- **Intel feed:** fetcher in `core/athena/intel/feeds.py`, parsed to `NormalisedAdvisory` (`core/athena/intel/model.py`), stored with `upsert_advisory` (`core/athena/intel/ingest.py`). Add a `SOURCE_AUTHORITY` entry (`core/athena/intel/authority.py`) and an `intel.poll.<src>` handler in `core/athena/workers/intel_jobs.py` calling `record_source_result`.
- **Investigation tool:** `TOOLS` and `TOOL_DESCRIPTIONS` in `core/athena/investigation/tools.py`. New signals go in `SIGNAL_NAMES` (`core/athena/investigation/verdict.py`), `signals_for` (`core/athena/workers/investigate.py`) and `Signals` (`core/athena/risk/scoring.py`). Add an eval case in `core/evals/corpus/`.
- **Node collector:** a Go function using fixed-argument `run(name, args...)` in `node/internal/collect/collect.go`, listed in `CAPABILITIES` (`core/athena/nodes/protocol.py`), `COLLECTION_ORDER` (`core/athena/nodes/dispatch.py`) and `_dispatch` (`core/athena/workers/node_ingest.py`).
- **Router and page:** `core/athena/api/routers/<name>.py` registered in `create_app` (`core/athena/api/app.py`); `web/pages/*.vue` using `api<T>()` (`web/composables/useApi.ts`), with navigation in `web/layouts/default.vue` and untrusted text through `web/components/UntrustedText.vue`.

### Phase 0: Foundations and guardrails

**0.1 Users, roles and authorization.**

- **Build:**
  - User and role management: invite, set role, disable, and reset MFA.
  - TOTP on the existing `mfa_*` columns, with the TOTP secret sealed using the envelope crypto in `core/athena/crypto/envelope.py`.
  - `require_role` (`core/athena/api/deps.py`) applied to every route.
  - Consumers for step-up (`has_fresh_step_up` in `core/athena/api/auth.py`).
  - Separation of duties.
  - CSRF protection in the BFF (`web/server/api/[...path].ts`) and `Idempotency-Key` handling on mutating POSTs.
  - A break-glass CLI command that needs host access, is audited, and restores an admin. `athena bootstrap` is not a recovery path: it refuses once any user exists.
- **Why:** NIST's agent-identity tenets ask for deterministic access decisions, and Elastic AlertZero logs approved actions as the approver's decision.
- **Touch:** migration `0021_users_mfa_idempotency`, `core/athena/api/routers/auth.py`, `core/athena/cli.py`.
- **Tests:**
  - A route-introspection test that fails if a route registered in `create_app` lacks a role dependency. Exemptions are explicit: health, login, bootstrap, and node endpoints, which use request signing.
  - TOTP enrol and verify.
  - A replayed key returns the original response.
  - Break-glass writes an audit entry.
- **Done when:** two users with different roles exist, and one cannot approve their own request.

**0.2 Allowlist the jobs API.**

- **Build:** `POST /jobs` (`core/athena/api/routers/jobs.py`) currently enqueues any registered kind with any payload. Replace that with an allowlist of user-enqueueable kinds, each with a payload schema and a required role.
- **Tests:** a registry test that no kind naming a mutation (apply, rotate, block, isolate, revoke) is registered in core.
- **Done when:** a non-allowlisted kind returns 403.

**0.3 Least-privilege database roles.**

- **Build:**
  - Give each service its own role: migrate (owner), api, worker, scheduler, signer and executor. Only migrate can alter tables or triggers, and every role gets only the DML it needs. `audit_event` is INSERT-only for all of them.
  - Create the roles in the migrate step or `deploy/deploy.sh`, not a Postgres init script, because init scripts run only on an empty volume.
  - On existing installs the conditional grants in `core/athena/db/migrations/versions/0003_executor_role.py` already ran as no-ops, and 0003 grants only SELECT on `job` and INSERT on `audit_event` anyway. So migration `0022_roles_and_grants` re-grants explicitly, including SELECT and UPDATE on the new grants table.
- **Touch:** `deploy/compose.yaml` (per-service credentials), `deploy/scripts/gen-secrets.sh`, and `athena doctor` failing when a role is missing.
- **Tests:** connecting as each role, forbidden statements fail; for example, api cannot `DROP TRIGGER`, and the executor cannot write `finding`.

**0.4 A signer service and grants.**

- **Build:**
  - A separate signer service holds `grant_private_key` and later the mandate key (3.5). Neither key is ever mounted into api or worker.
  - The signer re-validates each approval rather than trusting database state alone. It checks the approver's role and fresh step-up, separation of duties, the finding and advisory revision, and the dry-run hash.
  - Grant fields: action, target (asset or node id), parameters, approver, change record id, a hash of the approved dry-run output, `issued_at`, expiry, nonce and `key_id`.
  - The signer signs the canonical JSON that `GrantVerifier` checks.
- **Touch:** a new service in `deploy/compose.yaml`; the grants table in migration 0022.
- **Tests:** a sign and verify round trip; refusal of expired, replayed, wrong-target, wrong-key and dry-run-mismatched grants; the signer refuses an approval row inserted directly into the database without a matching step-up record.

**0.5 Executor skeleton.**

- **Build:**
  - Replace the idle loop in `executor/athena_executor/main.py`. The executor claims a grant, verifies it, and looks up the action in a registry inside `executor/athena_executor/`. It runs `plan` (dry-run) and checks that the output matches the grant's hash, then runs `apply`, then `verify`. `rollback` runs only when verify fails.
  - Ship only `noop` at first.
- **Egress:** the executor sits on the `internal: true` `private` network with no egress. Actions that need the outside world go through a dedicated egress proxy that enforces a per-action allowlist named in the grant, and logs every connection.
- **Secrets:** the executor has no master key and no access to `secret`. It gets its own sealed store: operators submit connector credentials sealed to the executor's public key, so core can store them but never read them.
- **Audit:** the executor cannot import `athena`, so it must reproduce `_canonical` and the advisory-lock scheme (`pg_advisory_xact_lock(hashtext('athena.audit'))`) from `core/athena/audit/chain.py` byte for byte.
- **Tests:**
  - A new `executor/tests/` suite.
  - A cross-implementation test in `core/tests/`, with the executor package installed as a test dependency, that hashes the same records both ways and requires identical chains.
- **Done when:** a `noop` grant runs end to end with audit entries, `GET /audit/verify` passes, and the executor still imports without core.

**0.6 Extend the boundary tests.** Extend `core/tests/test_boundaries.py`:

- Approval and remediation modules never import `athena.llm` or `athena.investigation` on an apply path.
- Executor action modules never import `athena`.
- Only the signer references the private-key paths.
- The investigation registry stays read-only. Strengthen `core/tests/test_investigation.py`, which checks only names today, to run every tool inside a read-only transaction with outbound network blocked and assert no writes and no remote calls.

**0.7 Kill switch and pause.**

- **Build:**
  - A global halt checked by the worker before it claims investigation jobs, by the gateway before any model call, by the signer before signing, and by the executor before applying.
  - Pause and cancel for a single investigation.
  - An admin route that requires step-up.
- **Why:** CrowdStrike's AI Kill Switch.
- **Touch:** migration `0023_control_state`.
- **Tests:** while halted, refusals are logged and queued work stays queued, never dropped.

**0.8 CI coverage.** Run `python -m evals.harness --deterministic-only` (`core/evals/harness.py`) against CI Postgres; `core/evals/README.md` says it runs in CI, but it does not. Also run `npm test` in `web/` and the executor tests, on Go 1.27.3.

**0.9 Fixture estate.** A reproducible compose profile beside `deploy/compose.yaml`, with known ground truth for every later acceptance test:

- vulnerable images;
- a repository with planted secrets and a `.pth` hook;
- an inert sample of a malicious package;
- a host profile for the node agent.

**0.10 Sandbox egress.** Give each networked sandbox (the git clone and the Syft image scan) an explicit egress allowlist and record its connections. Any later networked scanner must follow the same pattern.

### Phase 1: Close the trust loop

**Goal:** one complete, audited path from finding to verified fix, before Athena acts on anything else.

**1.1 The M5 approval loop.**

- **Build:**
  - Approvals and change records. The flow:
    1. A deterministic plan.
    2. A proposal with evidence and dry-run output.
    3. An approver who is not the requester, holds the role and has a fresh step-up approves it.
    4. The signer re-validates and issues a grant.
    5. The executor applies it.
  - Autonomy levels for each action class, following Elastic AlertZero:
    - **Level 0:** recommend only.
    - **Level 1:** one-click approval.
    - **Level 2:** pre-approved by a named policy owner, for narrow reversible actions. Each action is still a grant recorded as that owner's decision.
  - Operational controls from M5:
    - canary rollout before fleet-wide application;
    - maintenance windows and change freezes;
    - limits on concurrent actions;
    - grant revocation, checked by the executor and served to nodes;
    - on startup, the executor reconciles change records left `attempting` after a crash by running `verify` and recording what it finds.
- **Touch:** migration `0024_approvals_change_records`; an approvals page in `web/pages/`.
- **Tests:**
  - Separation of duties is enforced.
  - An approval goes stale when its finding or advisory revision changes, mirroring `_apply` in `core/athena/workers/investigate.py`.
  - Revoked and frozen grants are refused.
  - A simulated crash is reconciled.

**1.2 The M4 patch workspace.**

- **Build:**
  - A forge connector (GitHub, GitLab) whose token is held in the executor's sealed store.
  - A sandboxed workspace that clones, applies the upgrade using OSV-Scanner fix guidance, runs the project's tests, and offers a pull request with evidence.
  - Network policy for the workspace:
    1. Fetch dependencies with egress allowlisted to the relevant package registries.
    2. Run the tests with no network.
  - Opening the PR is the first real executor action, under a grant.
  - If Renovate 45 already has an equivalent PR open, link it instead of opening a duplicate.
  - The model may draft the change; deterministic checks (tests pass, diff scope matches the plan) decide whether the PR is offered.
- **Why:** Defense Factory ships PRs with tests; OpenSSF says never trust an AI patch without tests and human review. PRD open question 3 (direct PRs or diffs only) is answered here: PRs, under a grant.
- **Touch:** `core/athena/remediation/classify.py`, `core/athena/remediation/source.py`, a new `core/athena/remediation/workspace.py`, and migration `0025_patch_workspaces`.

**1.3 The verify job.**

- **Build:**
  - After an action or a merged PR, the `verify.finding` job rescans the scope. It sets `resolved` only after a complete scan, with the evidence attached.
  - Where a reproducer exists, it must show the exploit is blocked and the tests still pass, in the style of the CWE-bench verifier.
  - A failed verify reopens the finding and alerts.
  - A Dependabot alert disappearing is never evidence of a fix: from 8 December 2026, alerts pause on inactive repositories.
- **Touch:** migration `0026_verification_runs`.
- **Done when:** in the fixture estate, a vulnerable image goes through PR, rebuild and rescan to `resolved` end to end.

**1.4 Rollback.** Every action has a rollback. It runs automatically when verify fails, including on a health regression within the action's window, or when a human triggers it from the UI. Both paths are audited.

**1.5 Outbound notifications and ticketing.** Add Slack, Telegram, email and webhook channels to `core/athena/notify/service.py`, which is in-app only today, so approvers are reached. Add ticket creation through a connector. Messages carry ids and links only, never secrets or untrusted text.

### Phase 2: Identify breadth, low risk (in parallel with Phase 1)

- **Build:**

  - Identity becomes a **per-kind fingerprint**. Vulnerability findings keep the existing columns and constraint; other kinds use their own fingerprint, with a CHECK constraint that keeps `vulnerability_id`, `component_id`, `match_method`, `match_confidence` and `advisory_revision` required when the kind is vulnerability.

### Phase 3: Investigation depth

**3.1 New tools and evidence requests.**

- **New read-only registry tools:**
  - `lookup_indicator` (after 5.3);
  - `lookup_attack_technique`;
  - `get_reachability`: OSV-Scanner call analysis or Dependabot reachability as evidence. "Potentially reachable" counts as reachable, and reachability never suppresses on its own.
  - `query_events`, capped at 50 rows (after 5.1).
- **Live evidence is not a registry tool.** The model can file an *evidence request* that names an allowlisted osquery query id or Velociraptor artifact. Deterministic policy (3.4) and the mandate (3.5) decide whether it becomes a signed, read-only node task. Its result returns as evidence for a later step. Only an id crosses the wire, never SQL.
- **Why:** osquery 5.24.1; Velociraptor 0.77.4, which needs 0.77.3 or later after repeated 2026 CVEs.
- **Touch:** `TOOLS`, `TOOL_DESCRIPTIONS`, `SIGNAL_NAMES`, `signals_for`, `Signals`, migration `0030_evidence_requests`, and eval cases.

**3.2 Compromise assessment.**

- **Build:** when a finding is `applicable` and KEV-listed, or is a `MAL-` hit, a deterministic rule enqueues an assessment. It covers the period since the earliest known exploitation and uses evidence requests, inventory and vendor IOCs, plus telemetry once Phase 5 exists. The outcome is one of three: evidence found, no evidence, or insufficient telemetry. It is never "clean" without coverage.
- **Why:** vCenter CVE-2026-123890 was reportedly exploited from early September, months before the 19 November patch.

**3.3 ATR pre-filter.** Run pinned Agent Threat Rules over advisory text, scanner output, tool results and event payloads before they reach the loop, in a new `core/athena/llm/screen.py` called where `core/athena/investigation/loop.py` quotes untrusted text. A match is a signal and an audit entry, never a verdict. Watch for false positives: v4.3.1 narrowed 13 rules.

**3.4 Deterministic tool-call and evidence policy.**

- **Build:** CEL expressions over the tool name, its arguments, its results and the mandate, checked before every tool call and every evidence request, in `core/athena/llm/policy.py` and the dispatch in `core/athena/investigation/loop.py`. This is the NeMo Guardrails 0.25 tool-rail pattern. An LLM judge is advisory only, per NIST's tenet that keeps policy apart from reasoning.
- **Tests:** out-of-scope calls are denied; model-supplied arguments cannot widen scope.

**3.5 A mandate for each investigation.** Each investigation gets a mandate: finding id, asset scope, allowed tools and evidence ids, budget and expiry.

- It is signed by the **signer service** with a mandate key. The worker that starts investigations never holds that key.
- Delegation may only narrow it, and it is recorded in the audit chain.
- Migration `0031_investigation_mandates`.
- **Why:** NIST agent-identity tenets (secondary source) and the OWASP Securing Agentic Applications Guide v2.

**3.6 Adversarial evals with PyRIT 1.2.** A target for the investigation endpoint, using the CyberSecEval prompt-injection set and ATR rules, run nightly. The deterministic gates are no mutating call, no grant request, no evidence request outside the mandate, and a verdict equal to the control case in `core/evals/corpus/prompt-injection-control.toml`. LLM scorers are advisory and budget-capped.

### Phase 4: Mitigate

**4.1 Grant delivery and a privileged node helper.**

- **Delivery:** nodes pull work from the core API, so grant-bearing tasks travel that way. The executor writes the signed grant to its task table; core serves it to the node verbatim. Core relays but cannot forge, because it has no grant key.
- **The helper:** the agent itself stays unprivileged. A separately confined helper performs host actions:
  - It has its own systemd unit and its own minimal capability set.
  - It offers one fixed action per verb.
  - It is reached over a local socket.
  - It verifies each grant itself: the pinned grant public key, its own `node_id`, a nonce cache, expiry and revocation.
- **This is a trust-boundary change:** the helper is opt-in at install, reviewed separately, and every verb ships with its inverse.
- **Touch:** `node/internal/agent/agent.go`, `node/internal/client/client.go`, a new helper command under `node/cmd/`, `deploy/node/`, `core/athena/nodes/protocol.py`, `core/athena/nodes/keys.py`.
- **Tests:** Go tests for replay, wrong `node_id`, expiry, revocation and wrong key; the node-task key cannot sign a grant; the CI no-shell grep extends to the helper.

**4.2 First executor actions.**

| Action | Runs via | Precondition | Snapshot | Verify | Rollback |
|---|---|---|---|---|---|
| Host firewall block | Node helper | Not Athena's own management path | Ruleset | Rule present, connection refused | Remove rule |
| Stop or disable a service | Node helper | Not on the protected list | Unit state | Inactive | Restore state |
| Isolate a container | Node helper on the Docker host | Decision 6.3 settled; not part of Athena | Network attachments | Detached | Reattach |
| Block an indicator | Firewall, or sensor policy after 5.5 | Indicator valid and in scope | Policy | Active | Remove, or expire |
| Revoke federated credentials, rotate a secret, validate a secret live | Executor through a provider connector and the egress proxy | Owner confirmed | Metadata only | Old credential rejected | None: irreversible, level 0 or 1 only |
| Pin a package to a clean version | Patch workspace (1.2), or node helper for OS packages | Clean version known | Installed version | Version present | Reinstall previous, unless malicious |

**4.3 Playbooks in CACAO v2.** Playbooks are CACAO v2.0 data. Each step maps to a registered executor action or a human task, tagged with D3FEND. Tracecat is an optional external SOAR, reached over its API. Migration `0032_playbooks`. The first playbooks:

- **Malicious package:** assess, rotate exposed secrets, pin the clean version, hunt for `.pth` hooks.
- **KEV compromise:** assess, then contain.

**4.4 Reporting timers and CSAF VEX export.**

- **Two regimes, both configurable:**
  - **EU Cyber Resilience Act timers** apply only when the operator is a manufacturer reporting on its own product. Article 14 sets a 24-hour early warning and a 72-hour notification. For an actively exploited vulnerability, the 14-day final report runs from when a corrective measure is available.
  - **NIS2 timers** apply to incidents in the operator's own estate.
- **Athena's role:** it drafts and a human submits. The report destination is configurable, because the EU Digital Omnibus (unverified) may change routing. This is workflow support, not legal advice.
- **Export:** add a CSAF VEX export next to `core/athena/export/openvex.py`, with 2.0 as the default and 2.1 opt-in.
- **Touch:** migration `0033_regulatory_reports`.

### Phase 5: Runtime telemetry and detection (after decision 6.1 and Phase 1)

**5.1 Telemetry ingestion and an event store.**

- **Build:**
  - Ingest node events and sensor output: Tetragon or Falco JSON, Suricata EVE, Zeek JSON and osquery results.
  - Normalise them to OCSF.
  - Store them in a daily-partitioned Postgres table with a retention sweep (decision 6.4).
  - Keep a per-source watermark, so gaps show as gaps.
  - The scope is evidence for investigation, not a SIEM.
- **Touch:** a new `core/athena/telemetry/` package and a new router `core/athena/api/routers/telemetry.py`, the `ingest.telemetry` job kind, and migration `0034_event_store`.
- **Risks:** volume; log content is hostile input (ATT&CK v20 prompt-injection techniques).

**5.2 The detection worker.**

- **Build:**
  - Run pySigma 2.1.2 or later `sigma.matching` with RE2 and SafePolicy, behind an OCSF field-mapping pipeline.
  - Matches become detection findings tagged with ATT&CK ids, investigated rather than alerted raw.
  - First use cases: SafePay precursors and wfx-loot workflow tampering.
- **Touch:** a new `core/athena/workers/detect.py`, migration `0035_detection_rules`, and suppression through `core/athena/suppression/service.py`.
- **Risks:** pySigma is LGPL-2.1, and the matching module is weeks old.

**5.3 Indicator intel and ATT&CK.**

- **Build:**
  - Ingest indicators from MISP (2.5.52 or later), OpenCTI (an LTS release) and CISA STIX files.
  - Indicators get **their own confidence and expiry model**. `SOURCE_AUTHORITY` ranks version-range authority and does not fit them.
  - Load the ATT&CK v20 catalogue and a D3FEND 1.6.0 mapping.
  - Add ARTEX only after its format and licence are verified.
- **Touch:** `core/athena/intel/feeds.py`, a new `core/athena/intel/indicators.py`, handlers in `core/athena/workers/intel_jobs.py`, and migration `0036_indicators_and_attack`.
- **Tests:** a withdrawn indicator retracts its matches, mirroring `core/tests/test_source_withdrawal.py`.

**5.4 Cloud posture** (PRD Phase 3 scope; needs decision 6.1).

- **Build:**
  - Run Prowler (Apache-2.0) in the sandbox with read-only cloud credentials and an egress allowlist (0.10).
  - Ingest its OCSF output as misconfiguration findings, with cloud resources as assets. Never use Prowler's fixers.
  - Prioritise the GitHub OIDC trust-restriction check, the Bedrock and AgentCore identity checks, and the wfx-loot cloud indicators.
  - The RFC 10070 audience check is **Athena's own** misconfiguration check, not a Prowler check.
- **Touch:** migration `0037_cloud_accounts`.

**5.5 Virtual patching.**

- **Tetragon 1.8:** TracingPolicy enforcement as an executor action, run in observe mode first. Uprobe `Override` stays off: it is experimental and needs Linux 6.18 or later and glibc 2.34 or later.
- **Shirudo pilot**, lab-only behind a flag. It is pre-release, needs a patched kernel and TPM 2.0, and its effectiveness figures are the vendors' own.
  - A shield deploys only after its reproducer passes and a human approves it.
  - Signing keys stay with the executor.
  - `shirudo attest` evidence goes to the audit chain.
- **Why:** this is runtime control, so it happens only through grants.

**5.6 Close-out and coverage.** An incident close-out report: an audit-chain timeline, actions, evidence, ATT&CK techniques and D3FEND countermeasures. Add MTTR and time to mitigate to `core/athena/metrics/service.py`, and a coverage view from `web/components/CoveragePanel.vue`.

### Track S: Self-protection (throughout)

- **S.1 A dedicated sandbox runner.** The worker's read-write Docker socket (`deploy/compose.yaml`, line 94) exists only for `docker run` and `docker pull` in `core/athena/scanners/sandbox.py`. Image reads already go through the read-only proxy, which cannot launch containers (`POST: 0`). A sandbox-runner service takes the socket and exposes one narrow API: run a validated `SandboxSpec` with a pinned digest, an allowlisted network, no privileged mode and no host mounts. The worker loses the socket. This is M8's sandbox-launcher privilege reduction.
- **S.2 Self-scan.** Athena scans its own repository, images and dependencies on every release. A KEV-listed or malicious hit fails the release.
- **S.3 SLSA and Sigstore.** SLSA provenance and Sigstore signing for the images and the node binary. Verify them in `deploy/deploy.sh` and `deploy/node/install-node.sh`.
- **S.4 Behavioural baselines for Athena's own agents.** Build them from the audit chain and egress log: tool mix, model calls, evidence and grant requests, and egress destinations. Drift raises an alert, and optionally a pause (0.7).
- **S.5 Evaluate OpenShell** (CNCF Sandbox, secondary source) for confining LLM tool execution. Record the decision.

## 5. Invariants every phase keeps

1. **Boundaries are enforced by tests.** `core/tests/test_boundaries.py` enforces them, extended by 0.6:
   - the executor never imports `athena.llm`, `athena.investigation` or `athena`;
   - investigation never imports execution;
   - `executor/pyproject.toml` names no model client and not athena-core.
2. **CI keeps three checks.** The executor imports without core, its image contains no model client, and node code contains no generic execution path.
3. **The investigation registry is read-only, checked by behaviour, not only by name.** Live evidence arrives only through policy-approved evidence requests.
4. **The gateway is the only model path.** Secrets are blocked, not redacted. `local_only` is the default. The budget is enforced at the gateway, and every attempt is logged, refusals included.
5. **The model never decides an outcome.** It never sets band, severity or resolution. Triage never closes a finding. Malware cannot be dismissed by the model. A stale verdict is discarded.
6. **Node trust is anchored at enrolment.** Node tasks are signed by the key pinned at enrolment, and every capability has fixed arguments. Keys are generated on the host and stored 0600. The node-task, grant and mandate keys are distinct, and the grant and mandate keys live only in the signer.
7. **The audit chain is append-only.** Every consequential action calls `record()`, rejections use `record_isolated`, and every writer produces the same canonical hashes.
8. **Sandboxes are locked down.** No network by default. Today the git clone and the Syft image scan are networked; each networked sandbox has an explicit egress allowlist (0.10). All capabilities are dropped, the root filesystem is read-only, the uid is 10001, images are pinned by digest, and secrets are redacted.
9. **Athena is honest about what it has not seen.** A partial scan never means clean, and not observed never means clean. Exhausted budget or a halt queues work; it never drops it.
10. **Core is never reachable from a browser.** SSE events carry ids only, and any response of 400 or above rolls back the transaction.
11. **No mutating job kind is registered in core.** `POST /jobs` accepts only allowlisted kinds.
12. **Each service has its own least-privilege database role,** and only migrate can change schema or triggers.

## 6. Decisions to make

**6.1 Amend the PRD scope** (before Phase 5).

- **Options:**
  - Keep §50 as written, and drop Phase 5.
  - Amend it.
- **Recommendation:** amend it explicitly:
  - Detection and telemetry are in scope as evidence feeding investigation, not as a SIEM.
  - Runtime control happens only through executor grants.
  - Cloud posture moves forward from PRD Phase 3.

  Record the amendment as an ADR, and update §50 and `docs/MILESTONES.md`.

**6.2 OCSF as the internal schema** (before 2.1).

- **Options:**
  - OCSF everywhere.
  - Athena's own model, with OCSF only at the edges.
- **Recommendation:** use OCSF 1.10 for the event store and as `class_uid` on findings, but keep the relational finding tables, with per-kind fingerprints, as the source of truth.

**6.3 Asset isolation** (before the isolate action in 4.2). PRD open question 7 asks whether confirmed exploitation should trigger anything beyond notification, such as isolating the asset.

- **Recommendation:** allow isolation only as a level 0 or 1 action under a grant, never automatic, with tested rollback. Settle this in the PRD first.

**6.4 Event store** (before 5.1).

- **Options:**
  - Postgres partitions.
  - OpenSearch.
  - ClickHouse.
- **Recommendation:** Postgres daily partitions with short retention and a volume budget for each source, behind an interface so ClickHouse can replace it later. That keeps one database and one backup and role model.

**6.5 Runtime sensor** (before 5.1).

- **Options:**
  - Tetragon 1.8: observability and enforcement.
  - Falco 0.45: detection only.
- **Recommendation:** Tetragon by default, because one component serves both 5.1 and 5.5. Accept Falco events from users who already run it.

**6.6 Policy language** (before 3.4).

- **Options:**
  - CEL: as in NeMo Guardrails 0.25 and Tetragon `MatchCEL`; deterministic and not Turing-complete.
  - Extending the Python predicates in `core/athena/llm/policy.py`.
- **Recommendation:** CEL, stored as versioned data, after a maturity check of the Python implementation chosen.

**6.7 AGPL sidecars.**

- **Recommendations:**
  - **MISP:** a client of the user's own instance.
  - **Vulnerability-Lookup:** an optional sidecar.
  - **Velociraptor:** optional; the osquery allowlist comes first.
  - **TruffleHog:** not needed.
  - **Tracecat:** API only.
  - **Renovate:** interop only.
- **The rule:** separate service or subprocess, never imported or linked.
