# 1. Framework

**Nuxt 4, server-rendered, with Nitro as a backend-for-frontend.** This supersedes the Next.js suggestion in PRD §45; the PRD is updated to match.

The decisive reason is **topology, not rendering**. Athena Core holds credentials for every protected system and must not be internet-facing.

```text
SPA                                Nuxt BFF
browser ─────────────► core        browser ──► nitro ──► core
   core is exposed                    only nitro is exposed
   token lives in the browser         session cookie only, no client-side API token
```

Nitro additionally gives server-side sessions, a place to enforce CSP, SSR for a fast overview paint, and a seam for request-level authorisation logging. Nuxt over other SSR frameworks: first-class Nitro, per-route SSR/CSR, and Vue SFCs suit a small team building a largely CRUD-shaped app.

# 2. Architecture

```text
browser ──HTTPS, session cookie──► Nuxt 4 / Nitro ──private network──► core /api/v1

web/
├── pages/          file-based routes (§5)
├── layouts/        default · auth · onboarding
├── components/     finding/ approval/ asset/ chart/ ui/
├── composables/    useFindings · useApprovals · useMetrics · useEvents · useStepUp
├── stores/         Pinia: session, filters, saved views, connection status
├── server/
│   ├── middleware/auth.ts        session → core identity
│   ├── api/[...path].ts          proxy to core
│   ├── api/events.ts             SSE relay
│   └── plugins/security-headers.ts
└── types/api.d.ts  generated from the core OpenAPI document
```

Types are generated by `openapi-typescript` in CI, never hand-written — a backend contract change breaks the build, not production.

# 3. Auth

- Nitro forwards credentials to core, stores the session server-side, and sets an opaque `HttpOnly` / `Secure` / `SameSite=Lax` cookie. The browser never holds a token that can reach core.
- `server/middleware/auth.ts` resolves the session on every request: `/api/**` returns 401, page requests redirect.
- **Step-up re-authentication for every approval.** `useStepUp()` obtains a short-lived token from core and attaches it to that one request; it is never persisted client-side.
- Idle timeout 30 min, absolute 12 h. Logout revokes the server-side session, not just the cookie.
- Role is resolved server-side. Client-side role checks are **affordance only** — every authorisation decision is enforced in core.

# 4. Data and Realtime

Composables over a heavyweight query library; Nuxt's `useFetch` already handles SSR payload transfer, dedup, and cancellation.

```ts
// composables/useFindings.ts
export function useFindings(filters: Ref<FindingFilters>) {
  const { data, pending, error, refresh } = useFetch('/api/v1/findings', {
    query: filters,
    watch: [filters],
  })
  useEvents(['findings'], refresh)      // SSE-driven invalidation
  return { findings: data, pending, error, refresh }
}
```

Pinia holds only genuinely shared client state — session, filters, saved views, connection status. Server data is not duplicated into it.

**Filter state lives in the URL.** A filtered findings view is a shareable link, which is how a team actually uses this tool.

**Realtime** is SSE relayed by Nitro. Events carry `{topic, id, version, seq}`, not payloads — the client refetches, so authorisation is re-checked on the normal read path. Reconnect uses `Last-Event-ID`. A dropped connection degrades to 60-second polling **and says so**; a dashboard that looks live while being stale is dangerous.

Every data-bound component renders four distinct states: loading, empty, error, and — the one most products omit — **stale**.

Global chrome: `⌘K` command palette, persistent patrol indicator, and an approvals badge that is never suppressed.

```text
│ ubuntu-server         │ Service running        ✓     │                  │

│                       │ Feature enabled        ?     │  ✓ builds        │
│ base       0.98       │   "could not determine"      │  ✓ 142 tests     │
│ exploit    1.00 KEV   │ Known exploitation     ✓     │  ✓ rescan clean  │
│ exposure   1.00       │                              │                  │
│ importance 0.95       │ Verdict: applicable          │ [Request         │

```

Every ✓/✗/? links to the evidence row behind it, with tool, version, and timestamp. `?` is a distinct state, never rendered as ✗. The risk panel shows the stored arithmetic, not a restated label. If an investigation cannot be reconstructed, the UI says so and downgrades its presentation.

## Approval — the highest-consequence screen

```text
┌───────────────────────────────────────────────────────────┐
│ APPROVAL REQUIRED  ·  expires in 3h 42m                   │
│ Upgrade openssl 3.0.2 → 3.0.13                            │
│                                                           │
│ BLAST RADIUS  3 hosts · 7 services · restart nginx,       │
│   postgres · ~5s each, rolling · tier: production         │
│   window Sun 02:00–04:00 (+2d 6h)   ⚠ outside window now  │
│                                                           │
│ ROLLBACK  ✓ package downgrade  ✓ config snapshot          │
│   ⚠ postgres restart not reversible without brief outage  │
│                                                           │
│ VALIDATION  ✓ builds  ✓ 142 tests  ✓ rescan clean         │
│   ⚠ no test coverage for the affected path                │
│ [ diff viewer ]                                           │
│                                                           │
│  Reject      Approve (queue for window)     Approve now ⚠ │
└───────────────────────────────────────────────────────────┘
```

Approve requires step-up auth and, for production tier, typing the asset name. Out-of-window approval is visually marked as an override and records a reason. Anything not reversible is stated prominently — silence where reversibility is unknown is not permitted. Under separation of duties, a requester sees the approve action **disabled with an explanation**, not hidden.

## Remaining screens

**Findings** — filters in one row; default grouped by vulnerability (one CVE across 14 hosts is one row); header states the coverage denominator. **Assets** — table by default, graph as an alternate capped view; assets with unset tier or owner surface as a configuration gap, since unset importance silently deflates risk. **Patrols** — run history including what was skipped or failed. **Intel** — advisory browser plus feed health and age. **Chat** — streaming, every claim a citation chip; read-only, proposals route through the normal approval flow. **Audit** — filterable log with a Verify-chain action and export.

# 7. Metrics

`/metrics` implements PRD §51. Every tile states its target and whether it is met; a metric with no target is decoration.

```text
┌──────────────────────────────────────────────────────────────┐
│ METRICS                   [7d 30d 90d 1y]  [tier ▾] [team ▾] │
├──────────────────────────────────────────────────────────────┤
│ Detection p95   MTTR        False positive                   │
│    1.4 h         6.2 d          18%                          │
│  target <2h ✓  target <7d ✓  target <30% ✓                   │
│ Coverage <24h   Patch success   AI spend (mo)                │
│    93%             78%           $41.20 / $150               │
├──────────────────────────────────────────────────────────────┤
│ POSTURE OVER TIME     stacked area, severity ramp, 90d       │
├──────────────────────────────────────────────────────────────┤
│ DETECTION LATENCY  p50+p95   │ REMEDIATION FUNNEL  bar       │
│ COVERAGE FRESHNESS heatmap   │ BACKLOG AGE         bar       │
│ AI SPEND vs budget  area     │ SLA COMPLIANCE      bar       │
└──────────────────────────────────────────────────────────────┘
```

| Metric | Definition | Form | Target |
|---|---|---|---|
| Detection latency | published → affected asset identified, p50/p95 | line + target rule | p95 < 2 h |
| Mean time to remediate | `CONFIRMED` → `RESOLVED` | line | < 7 d critical |
| False positive rate | dismissed as FP ÷ investigated | line | < 10% mature |
| Coverage freshness | inventoried < 24 h ÷ total | tile + heatmap | > 99% mature |
| Patch success | build+test pass ÷ prepared | tile + bar | > 90% mature |
| Notification action rate | acted on ÷ sent | line | > 70% |
| AI spend | egress-gateway cost this period | area + budget rule | under cap |
| Investigation cache hit | cached ÷ total | tile | > 80% |
| **Confidence calibration** | human agreement per confidence band | grouped bar | HIGH > 95% |
| SLA compliance | remediated within band SLA ÷ due | bar | trend up |

Calibration is the chart that keeps the product honest — the visible answer to "should I believe Athena?"

One global time range for the page, no per-chart ranges. Every chart offers a table view and CSV export. Insufficient data renders "not enough data", never a flat line at zero. Coverage-sensitive metrics show their denominator inline.

# 8. Colour

Three jobs, three systems, no overlap — this is what stops a chart series reading as "critical".

| Job | System | Where |
|---|---|---|
| **Severity** (ordered magnitude) | single-hue red ordinal ramp | bands, chips, posture charts |
| **Outcome** (state) | reserved status palette | resolved, failed, regressed, stale |
| **Series** (identity) | categorical slots, fixed order | multi-series charts |

### Severity ramp — validated

Severity is ordered magnitude, so it is a one-hue ordinal ramp: **lightness carries the signal**, making it robust under every colour vision deficiency. CRITICAL is always furthest from the surface, INFORMATIONAL always nearest — so low-severity volume visually recedes, enforcing "action, not volume" in the palette itself.

| Band | Light `#fcfcfb` | Dark `#1a1a19` |
|---|---|---|
| CRITICAL | `#66201f` | `#f9bcb3` |
| HIGH | `#8e2f2c` | `#eb9086` |
| MEDIUM | `#b54840` | `#d4695f` |
| LOW | `#d1685f` | `#ae4a43` |
| INFORMATIONAL | `#e5948c` | `#8a3733` |

Both ramps pass the ordinal gate: monotone lightness, adjacent ΔL ≥ 0.06, hue spread ≤ 3°, surface-adjacent step clearing 2:1 (light 2.29:1, dark 2.22:1). Dark values are **selected for the dark surface**, not inverted. Re-run the validator if these change.

### Outcome status (reserved, never themed)

`good #0ca30c` resolved/verified · `warning #fab219` stale, expiring, near budget · `serious #ec835a` verification or patch failed · `critical #d03b3b` regression, rollback, chain failure.

Always icon + label, never colour alone — doubly so here, since status critical shares a hue family with the severity ramp.

### Series (fixed order, never cycled)

| Slot | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| Light | `#2a78d6` | `#eb6834` | `#1baf7a` | `#eda100` | `#e87ba4` | `#008300` | `#4a3aa7` | `#e34948` |
| Dark | `#3987e5` | `#d95926` | `#199e70` | `#c98500` | `#d55181` | `#008300` | `#9085e9` | `#e66767` |

Assigned by entity, never by rank — a filter that removes a series must not repaint the survivors. Line/bar/stacked may use 8; **scatter and small multiples cap at 3**, remainder folded to "Other" or faceted. A ninth series is never a generated hue. Sequential encoding (coverage heatmap) uses blue `#cde2fb → #0d366b`.

### Chrome

Surface `#fcfcfb`/`#1a1a19` · plane `#f9f9f7`/`#0d0d0d` · ink `#0b0b0b`/`#ffffff` · secondary `#52514e`/`#c3c2b7` · muted `#898781` both · gridline `#e1e0d9`/`#2c2c2a` · axis `#c3c2b7`/`#383835`.

`system-ui` throughout including large figures; `tabular-nums` only where numbers align vertically. Values, labels, and legend text wear text ink, never the series colour — a swatch beside them carries identity.

Tokens are defined on bare `:root`, redefined under `@media (prefers-color-scheme: dark)` guarded by `:root:not([data-theme="light"])`, and again under `:root[data-theme="dark"]`. No colour is defined only inside a media block.

# 9. Charts

| Data's job | Form |
|---|---|
| one headline number | stat tile, no plot |
| change over time | line |
| change over time, composition | stacked area, ≤ 5 bands, 2px gaps |
| magnitude across categories | horizontal bar |
| stage drop-off | bar funnel |
| two dimensions, one magnitude | heatmap, sequential ramp |
| distribution of ages/scores | histogram |

**Never a dual-axis chart** — two measures of different scale become two charts or one indexed to a common base. Never a pie or donut; the posture breakdown is a stat-tile row, which compares faster.

Marks: 2px lines, ≥8px markers, thin bars with 4px rounded data-ends on the baseline, **2px surface gap between adjacent fills**, recessive hairline grid in muted ink. Direct labels are selective — latest point, extremes, target line — never a number on every point. Target and budget lines are dashed muted rules with a direct label, never a coloured series.

Every chart ships a hover layer by default (crosshair + tooltip on line/area, per-mark on bar/dot/cell), a legend at ≥ 2 series with direct labels up to 4, and a **table view** toggle that doubles as the accessibility fallback and CSV source. A 45°/135° texture fill is available for CVD, print, and `forced-colors` — never on by default.

**Library: ECharts via `vue-echarts`**, tree-shaken, client-only, wrapped in `<ChartFrame>` which owns title, legend, table toggle, export, and empty/loading/stale states. Charts read resolved CSS custom properties so theme switching needs no re-instantiation. Alternatives considered: Unovis (younger), Observable Plot (weaker interaction), hand-rolled SVG (unjustified for ten chart types). Charts are client-only — the stat tiles above the fold are server-rendered and carry the first paint.

# 10. Non-Negotiable Rules

Each is enforced by a lint rule, a shared component, or a test.

**1 · Unknown is never rendered as clean.** Three states, three treatments: `observed clean` ✓ status good · `observed vulnerable` ● band colour + label · `not observed` ⃠ hatched texture + "not scanned" + timestamp. A `not_observed` value may never render as `0`, empty, or green.

**2 · Freshness is always visible.** `<FreshnessIndicator>` on any component displaying a fact: relative age, exact timestamp on hover, warning treatment past the staleness threshold. A host unseen nine days is visually distinct from one seen five minutes ago, everywhere.

**3 · Aggregates carry their denominator.** "1 critical" is incomplete; "1 critical across 38 of 41 assets" is the truth.

**4 · Consequential actions are deliberate.** Step-up auth, typed confirmation on production tier, a reason field for overrides, a visible expiry countdown on every pending approval.

**5 · Uncertainty is shown, not smoothed.** Model uncertainty, low match confidence, and un-investigated findings each get a distinct treatment. An un-investigated finding is never counted as confirmed.

**6 · Degradation is announced.** Lost SSE, stale intelligence, offline node, model unavailable, or budget exhausted each surface a persistent banner naming the degradation *and its consequence*.

# 12. Accessibility

WCAG 2.2 AA — text ≥ 4.5:1, UI and graphical objects ≥ 3:1. Severity is never colour-alone (chip + icon + label travel together; the one-hue ramp means lightness alone distinguishes bands under any CVD). Full keyboard operation including approvals and the command palette, visible focus, skip links. Charts carry a table view, an `aria-label` summarising the trend, and the texture channel. Live regions announce arrivals politely; `role="alert"` used sparingly. Respects `prefers-reduced-motion`; nothing essential conveyed by animation. 200% zoom without loss of function; responsive to 1024px.

# 13. Frontend Security

**Athena renders attacker-controlled content** — CVE descriptions, README excerpts, package metadata, commit messages, diffs. This is the UI's highest-risk surface.

- All of it goes through `<UntrustedText>`, which emits text nodes. **No `v-html` anywhere**, enforced by an ESLint rule that fails the build.
- Untrusted markdown is not rendered as markdown. Links display as text with the destination shown, never as live anchors.
- Diff and code rendering uses a tokeniser emitting text nodes only.
- Externally-originating content carries a provenance affordance, so a user knows they are reading attacker-supplied prose.

```text
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self';
  img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none';
  object-src 'none'; form-action 'self'
Strict-Transport-Security · X-Content-Type-Options · Referrer-Policy: same-origin
```

No CDN, no external fonts, no third-party analytics. CSRF protection on state-changing proxy routes; rate limiting on login and step-up at the Nitro layer; no secrets in the bundle or SSR payload (audited in CI); no production source maps.

# 14. Budgets and Testing

```text
Initial JS (gzip, overview)    < 180 kB      Route transition      < 200 ms
LCP, overview, cold            < 1.5 s       Findings list, 500 rows < 300 ms (virtualised >100)
Chart first render             < 400 ms      8h session            no unbounded growth
```

Enforced by Lighthouse CI and a bundle-size check per PR. Chart library, graph view, and diff viewer are dynamically imported.

Vitest for composables and components (all four states each); `openapi-typescript` diff as the contract gate; Playwright for E2E (login → finding → patch → step-up approval → verification), visual snapshots in both themes, and `axe-core` with zero violations per route.

Mandatory regression tests, from §10:

1. An unscanned asset renders as **not observed**, never clean.
2. A stale host is visually distinct on every surface.
3. Approve is unreachable without step-up.
4. A finding whose CVE description contains `<script>` renders it as text.
5. Every overview aggregate displays a denominator.

# 15. Deployment

Multi-stage Node 22 Alpine build producing `.output/`, run as a non-root user on port 3000. Runtime configuration only, so one image serves every deployment:

```text
NUXT_ATHENA_API_URL        internal core URL
NUXT_SESSION_SECRET_FILE   session signing key
NUXT_PUBLIC_APP_NAME       display name
NUXT_TLS_*                 optional direct TLS, or terminate upstream
```

`web` is the only service publishing a port. `/healthz` for liveness; readiness gated on core reachability so a partially-started stack does not serve a broken UI.

# 16. Open Questions

1. **Nuxt UI vs bespoke components.** Nuxt UI accelerates CRUD surfaces but constrains finding-detail and approval — the differentiated screens. Proposal: Nuxt UI primitives, bespoke domain components.
2. **Graph view value.** Expensive to build, easy to make useless above a few hundred nodes. Consider deferring to Phase 2 and shipping relationship lists first.
3. **Mobile.** Approvals are the one genuinely mobile-shaped task — a critical alert arrives away from a desk. MVP requirement or fast follow?
4. **Chat placement.** Dedicated route, or a context-aware panel on every screen? The panel is better product and more work.
5. **Approvals from notifications.** Needs an authenticated interaction path; the step-up requirement makes it non-trivial. Defer or design now?
6. **Severity ramp at chip size.** Validated for chart marks; small chips with 4px of colour need a check against the real UI before locking.
